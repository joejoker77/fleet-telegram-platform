## Item 1 — Composio: multiple accounts of the same toolkit per user (aliases)

### Goal
Let one human (one Telegram user) connect e.g. **two Gmail** or **two Instagram**
accounts and have the assistant pick which one to use — without losing per-user
isolation.

### Research verdict (2026-06-15, Composio official docs + changelog)
- Composio **natively supports** multiple connected accounts of the same toolkit
  under ONE `user_id`. The "new connect replaces the old" behaviour is the DEFAULT
  single-account mode, **not** a hard limit.
- Native multi-account shipped **2026-04-09** (Multi-Account Mode + connection
  aliases); `link()` (our path) got the `allow_multiple` guard on **2026-04-28**.
  Dmitrii's earlier "compound user_id" idea predates this — it was a reasonable
  workaround THEN, unnecessary NOW.
- **Keep `user_id = raw Telegram chat_id`** (see feedback_composio_user_id_scheme).
  Do NOT encode integration type/index into user_id — that would entangle the
  security-critical identity (the isolation boundary) with a mere selector.
  Distinguish accounts by `connected_account_id` + human `alias` ("work"/"personal").

### Implementation tasks
1. `composio-connect` (helper): accept an `--alias` and pass `allow_multiple=true`
   on the Connect Link `link()` call so a 2nd same-toolkit connect creates a new
   connected account instead of being rejected (`ComposioMultipleConnectedAccountsError`).
2. `composio-session` (helper): enable session multi-account mode — `multi_account`
   config (`enable: true`, `max_accounts_per_toolkit` 2–10, `require_explicit_selection`).
3. Bot/agent: when a toolkit has >1 active account, select by `connected_account_id`
   or alias at execution (the tool-router `account` param). Surface a friendly chooser
   to the user ("which Gmail — work or personal?") when ambiguous.
4. UX: never expose "connected_account_id" raw to the user — use aliases.

### Acceptance
One Telegram user connects two Gmail accounts (aliases work/personal), both ACTIVE
simultaneously; the assistant reads from the chosen one; isolation from other users
(by user_id) unchanged.

## Item 2 — Admin/root tier for selected tenants (NEEDS DECISION before build)

### Requirement (Vitaliy 2026-06-15)
Per server, the ability to designate one or more fleet accounts (= users/assistants)
as **admin with root access**. On the current server: vitaliy + dmrudenko (Dmitrii).
Motivation: operators need to manage the server (fix/debug/install, reach other
hosts) — a fully locked sandbox cripples that (cf. the ssh/egress thread).

### Where it stands today
- `provision-tenant.sh <user> <tg_id> [--admin]` already sets `is_admin` in the
  control-plane `users` table — but it grants nothing operationally yet.
- Tenant pods run hard-locked: `--cap-drop=ALL --security-opt=no-new-privileges
  --user <uid> --read-only`. Egress is now full-outbound (owner decision); ssh
  client + ~/.ssh mount added. So "reach other servers" is already unlocked for
  everyone; "root" is the remaining ask.

### Clarified requirement (Vitaliy 2026-06-15)
`is_admin` user = the SAME capabilities as a normal ubuntu sudo user → can run ANY
command via sudo. AND the assistant must run sudo **non-interactively** — apply the
sudo "password" at any moment WITHOUT a human typing it.

### Hard fact: the locked pod cannot give HOST sudo
Pod runs `--user <uid> --cap-drop=ALL --security-opt=no-new-privileges --read-only`
and has no `sudo` in the image. `no-new-privileges` + `cap-drop=ALL` block setuid
sudo outright; even if relaxed, sudo inside a pod = root in the CONTAINER, not the
host. "Manage the server like an ubuntu sudo user" is inherently HOST-level. So this
needs a model that reaches the host.

### Two viable models (pick one)
**Model A — admin runs on the HOST (recommended).** The admin assistant runs as its
ubuntu user directly on the host (the pre-pod host runtime), NOT in the locked pod.
`sudo` works natively. Simplest; exactly "a normal ubuntu user with sudo". Implication:
an admin (e.g. dmrudenko) is EXEMPT from the pod sandbox — which is reasonable, since
sandboxing a user who holds host root is moot. Means rolling dmrudenko back from the
pod to the host runtime.

**Model B — admin stays in the pod + ssh-to-host bridge.** Keep the admin in the pod
(sandboxed own env), give it an ssh key to a host account that has NOPASSWD sudo; the
assistant runs `ssh hostadmin@<host> sudo <cmd>`. Leverages the ssh client + ~/.ssh
mount + full egress we just shipped. Keeps the pod for the assistant's own files;
host-root via the ssh channel. More moving parts, but preserves the pod model.

(Model C — relax the pod to container-root — REJECTED: container-root ≠ host mgmt.)

### Mechanism for "sudo without a human typing the password": NOPASSWD
Use **NOPASSWD sudo** via `/etc/sudoers.d/<user>` (`<user> ALL=(ALL) NOPASSWD: ALL`).
The assistant just runs `sudo <cmd>` — no password is ever needed, which is exactly
"apply sudo at any moment without user input", and stores **no password anywhere**
(more secure than keeping a sudo password around). NB a vault-supplied password is
NOT viable: OneCLI injects only at the egress proxy and has no "reveal value" op, so
it cannot feed a password to `sudo -S` — NOPASSWD is the clean path.

### Provisioning
- `make-admin.sh <user>`: ensure host user in the `sudo` group + drop
  `/etc/sudoers.d/<user>` NOPASSWD + `visudo -cf` validate; set `is_admin=true` in
  the control-plane DB. `unmake-admin.sh <user>`: remove the drop-in + flag (one-command rollback).
- Gate strictly on `is_admin`. Per-server admin list (this server: vitaliy, dmrudenko).

### Guardrails — KEEP even for admins (research 2026-06-15)
Granting an autonomous AI agent root is high-risk: blast radius = the permissions it
holds; prompt injection against a root agent is root RCE (arXiv 2605.09721; AWS
agentic-AI security guidance; Zscaler least-privilege; PolicyLayer MCP priv-esc).
So even for admins:
- **shellfirm stays ON** — it still blocks `rm -rf /`, fork bombs, etc. as root. Do
  NOT disable the guard for admins (it's the last line against an injected destructive command).
- **Audit every sudo** to the WORM collector (sudoers `log_output`, or a sudo wrapper
  emitting to the audit socket).
- Optional **HITL / Telegram-approval** on the most destructive verbs (reuse the
  existing approvals mechanism) — decide per appetite.
