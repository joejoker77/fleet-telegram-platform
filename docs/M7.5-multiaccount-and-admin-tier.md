## Item 1 — Composio: multiple accounts of the same toolkit per user (aliases)

### Goal
Let one human (one Telegram user) connect e.g. **two Gmail** or **two Instagram**
accounts and have the assistant pick which one to use — without losing per-user
isolation.

### Research verdict (2026-06-15, Composio official docs + changelog)
- Composio **natively supports** multiple connected accounts of the same toolkit
  under ONE `user_id`. The "new connect replaces the old" behaviour is the DEFAULT
  single-account mode, **not** a hard limit.
- Native multi-account shipped **2026-04-09** (Multi-Account Mode + connection
  aliases); `link()` (our path) got the `allow_multiple` guard on **2026-04-28**.
  Dmitrii's earlier "compound user_id" idea predates this — it was a reasonable
  workaround THEN, unnecessary NOW.
- **Keep `user_id = raw Telegram chat_id`** (see feedback_composio_user_id_scheme).
  Do NOT encode integration type/index into user_id — that would entangle the
  security-critical identity (the isolation boundary) with a mere selector.
  Distinguish accounts by `connected_account_id` + human `alias` ("work"/"personal").

### Implementation tasks
1. `composio-connect` (helper): accept an `--alias` and pass `allow_multiple=true`
   on the Connect Link `link()` call so a 2nd same-toolkit connect creates a new
   connected account instead of being rejected (`ComposioMultipleConnectedAccountsError`).
2. `composio-session` (helper): enable session multi-account mode — `multi_account`
   config (`enable: true`, `max_accounts_per_toolkit` 2–10, `require_explicit_selection`).
3. Bot/agent: when a toolkit has >1 active account, select by `connected_account_id`
   or alias at execution (the tool-router `account` param). Surface a friendly chooser
   to the user ("which Gmail — work or personal?") when ambiguous.
4. UX: never expose "connected_account_id" raw to the user — use aliases.

### Acceptance
One Telegram user connects two Gmail accounts (aliases work/personal), both ACTIVE
simultaneously; the assistant reads from the chosen one; isolation from other users
(by user_id) unchanged.

## Item 2 — Admin/root tier for selected tenants (NEEDS DECISION before build)

### Requirement (Vitaliy 2026-06-15)
Per server, the ability to designate one or more fleet accounts (= users/assistants)
as **admin with root access**. On the current server: vitaliy + dmrudenko (Dmitrii).
Motivation: operators need to manage the server (fix/debug/install, reach other
hosts) — a fully locked sandbox cripples that (cf. the ssh/egress thread).

### Where it stands today
- `provision-tenant.sh <user> <tg_id> [--admin]` already sets `is_admin` in the
  control-plane `users` table — but it grants nothing operationally yet.
- Tenant pods run hard-locked: `--cap-drop=ALL --security-opt=no-new-privileges
  --user <uid> --read-only`. Egress is now full-outbound (owner decision); ssh
  client + ~/.ssh mount added. So "reach other servers" is already unlocked for
  everyone; "root" is the remaining ask.

### Mechanism options (tradeoffs)
| Option | What | Blast radius | Notes |
|---|---|---|---|
| A. Root INSIDE the pod | drop `no-new-privileges`, add caps / `--user 0` / writable rootfs for admin pods | container + mounted volumes + full egress | namespaced from host (unless userns maps to host root); least-bad "root" |
| B. Host sudo | grant the admin tenant's linux user sudo on the host | whole host | what Dmitrii effectively had pre-pod; biggest risk |
| C. Scoped fleet-admin | admin manages other tenants via cp-api (provision/restart/logs), NOT raw root | control-plane API surface only | safest; but not "root for arbitrary ops" |

Likely answer for operators = **A** (root in their own pod) and/or **B** (host sudo),
gated to the `is_admin` flag. C is complementary (fleet management).

### Security findings (research 2026-06-15)
Granting an autonomous AI agent root is high-risk: **blast radius = the permissions
the agent holds**; a prompt injection against a root agent is root RCE (arXiv
2605.09721 "privileged execution environments"; AWS agentic-AI security guidance;
Zscaler least-privilege; PolicyLayer MCP privilege-escalation). Consensus mitigations
even for admins:
- Least privilege / just-enough; prefer **just-in-time** elevation over standing root.
- **HITL / step-up approval** on destructive/admin verbs (we already have the
  Telegram approval mechanism — reuse it for admin actions).
- **Audit every privileged action** (we have the WORM audit collector — route admin
  ops through it).
- Keep the deterministic guards (shellfirm) ON even for admins; don't blanket-disable.
- Bounded blast radius: admin in own pod (A) over host root (B) where feasible.

### Open decisions for Vitaliy (before build)
1. Scope of "root": own-pod root (A), host sudo (B), fleet-admin via cp-api (C), or a combo?
2. Standing root vs just-in-time elevation (approval to enter an elevated shell)?
3. Which guardrails still apply to admins? (Recommend: keep shellfirm + audit; HITL on destructive verbs.)
4. Who is admin per server, and how is the list managed (the `is_admin` DB flag + a deploy step)?
5. Does the admin assistant act AS root autonomously, or only with per-action human approval?

### Next step
Decide 1–5, then design the admin-pod variant (separate `claude-pod-admin@.service`
or a flag on the wrapper) + the cp-api admin surface, with audit + HITL wired in.
