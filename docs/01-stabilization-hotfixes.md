# 01 — Стабилизация (Фаза 0): диагностика и хотфиксы

Цель фазы — устранить текущие проблемы прод-стека **на действующем сервере, без архитектурной миграции**, чтобы получить стабильную базу для перехода. Хотфиксы совместимы с целевой архитектурой (не создают долга).

---

## Проблема A — отвал TG-плагина при `claude -p`

### Симптом
Когда бот (или оператор) запускает в консоли `claude -p ...`, Telegram-плагин основной сессии «отваливается» и сам не поднимается; бот глохнет до полного рестарта сервиса.

### Корневая причина
Плагин — это MCP-сервер [`server.ts`](/opt/workspace/scripts/telegram-plugin/server.ts), который держит **единственного** потребителя `getUpdates` по bot-токену. При запуске второго процесса `claude` (в т.ч. `claude -p`) в том же проекте поднимается **второй** экземпляр `server.ts`, и он на старте принудительно убивает прежнего держателя токена:

```ts
// /opt/workspace/scripts/telegram-plugin/server.ts (фрагмент, строки ~12-72)
const PID_FILE = join(STATE_DIR, 'bot.pid')
// ...
try {
  const stale = parseInt(readFileSync(PID_FILE, 'utf8'), 10)
  if (stale > 1 && stale !== process.pid) {
    process.kill(stale, 0)
    process.stderr.write(`telegram channel: replacing stale poller pid=${stale}\n`)
    process.kill(stale, 'SIGTERM')   // <-- убивает ЖИВОЙ поллер основной сессии
  }
} catch {}
writeFileSync(PID_FILE, String(process.pid))
```

Дальше: короткоживущий `claude -p` завершается → его собственный плагин гасится по EOF stdin → **поллера не остаётся вовсе**. Основной `claude` при этом жив (tmux-сессия `claude` цела), поэтому `systemd` с `Restart=always` ничего не перезапускает — он видит работающий главный процесс.

`enableAllProjectMcpServers: true` в [`settings.local.json`](/opt/workspace/.claude/settings.local.json) усугубляет: дочерний `claude` тянет всю проектную конфигурацию MCP.

> Решение (комбинированное): **официальный плагин не патчим.**
> 1. **Основное — предотвращение:** сделать так, чтобы флаг `-p` вообще никак не затрагивал TG-плагин.
> 2. **Страховка — supervisor (watchdog):** внешний надзор за сервисами на случай любого другого отвала.

### Уровень 1 (основной) — `-p` не затрагивает TG-плагин вообще
Цель: дочерний `claude -p` запускается так, что его экземпляр плагина **либо не поднимается, либо физически не может тронуть поллер основной сессии**. Это конфигурация запуска, а не правка плагина. Два независимых рычага (применять оба — «пояс и подтяжки»):

**(a) Не активировать Telegram-канал в дочернем запуске.**
Канал поднимается флагом `--channels plugin:telegram@...` (его ставит только лаунчер) и/или авто-загрузкой проектных MCP (`enableAllProjectMcpServers: true` в [`settings.local.json`](/opt/workspace/.claude/settings.local.json)). Для `-p`/дочерних запусков:
- не передавать `--channels`;
- запускать со `--strict-mcp-config` и MCP-конфигом, где telegram отсутствует (не наследовать проектные MCP);
- либо отдельный `CLAUDE_CONFIG_DIR` для неинтерактивных запусков без включённого плагина.

**(b) Изолировать окружение токена в дочернем запуске.**
Даже если экземпляр плагина всё же стартует — он не должен видеть тот же токен и тот же `bot.pid`:
- запускать дочерний `claude -p` **без** `TELEGRAM_BOT_TOKEN` в окружении (плагин при отсутствии токена просто выходит — см. строки 48-55 `server.ts`);
- и/или с **отдельным** `TELEGRAM_STATE_DIR`, чтобы любой его `bot.pid` указывал в свой каталог и не пересекался с основным поллером.

Удобно зафиксировать это как **фиксированный способ вызова** `-p` (обёртка `claude` на PATH или строгий шаблон флагов/окружения, которым агент и оператор запускают неинтерактивный Claude). Это не трогает плагин — меняется только то, *как мы его вызываем*.

> Эффект: после `claude -p` основной поллер не падает, рестарт не требуется, блипа нет. Точные флаги свериться с версией CLI на этапе внедрения (это проектное решение, реализация — отдельно).

### Уровень 2 (страховка) — watchdog-supervisor
`systemctl restart claude-tg@<user>.service` поднимает канал — это рабочее лекарство. Нюанс лишь в **триггере**: `Restart=always` срабатывает только когда умирает сам `ExecStart`-процесс, а здесь умирает **дочерний** поллер при живом **родителе** (`claude` в tmux) — systemd этого не видит. Поэтому нужен **внешний детектор нездоровья**, который сам дёргает рестарт. Срабатывает на **любой** отвал (краши, OOM, ppid-самоубийство, выход по лимиту), а не только на `-p`; если Уровень 1 отработал, по `-p` он просто не понадобится.

Один общий на флот `systemd .timer` (раз в ~20-30 с) проверяет здоровье и при нездоровье рестартит — используя то, что плагин уже пишет сам (`bot.pid`):

```bash
#!/usr/bin/env bash
# /usr/local/bin/claude-tg-watchdog  (вызывается из claude-tg-watchdog.timer)
# Официальный плагин НЕ трогаем — только наблюдаем bot.pid и рестартим юнит.
systemctl list-units --type=service --state=running --no-legend 'claude-tg@*' \
  | awk '{print $1}' | while read -r unit; do
  user="${unit#claude-tg@}"; user="${user%.service}"
  pidfile="/home/$user/.claude/channels/telegram-$user/bot.pid"
  healthy=0
  if [ -f "$pidfile" ] && kill -0 "$(cat "$pidfile" 2>/dev/null)" 2>/dev/null; then
    healthy=1
  fi
  if [ "$healthy" != 1 ]; then
    logger -t claude-tg-watchdog "poller down for $user — restarting $unit"
    systemctl restart "$unit"   # тот самый рестарт, что вы делаете руками
  fi
done
```

Дополнительно к unit (тоже без патча плагина):
- `MemoryHigh=`/`MemoryMax=` + `MemoryAccounting=true` — против OOM (см. Проблему B);
- логировать каждый авто-рестарт (journald/аудит), чтобы рестарты были **видимыми и объяснимыми**.

Этот же watchdog закрывает и Проблему B: любой отвал/смерть процесса лечится авто-рестартом в пределах одного тика.

### Куда это ведёт в целевой архитектуре
Пока официальный плагин не переписан, канал остаётся **stdio-MCP-ребёнком основной сессии `claude`** (его нельзя сделать самостоятельным демоном без патча). Поэтому в целевом рантайме сохраняется тот же подход: **предотвращение** (дочерний `claude -p` не активирует канал и не видит токен — это и устраняет Проблему A по построению) + **watchdog-supervisor** как страховка. Хотфикс-supervisor — ранняя реализация той же идеи и переносится без переделок. Полностью «отдельный надзираемый channel-процесс» возможен только при будущем переписывании канала (вне скоупа миграции) — см. [03-component-mapping.md](03-component-mapping.md).

## Проблема B — случайные рестарты бота

### Симптом
Иногда бот уходит в рестарт без явной причины.

### Подход: сначала инструментировать, потом чинить
Корневая причина пока не зафиксирована — нельзя «чинить вслепую». Первый шаг — сбор доказательств:
- Включить персистентный journald и логировать код выхода:
  `journalctl -u 'claude-tg@*' -o short-precise` + `systemctl show claude-tg@<user> -p NRestarts,ExecMainStatus,ExecMainCode`.
- Проверить OOM: `journalctl -k | grep -i 'oom\|killed process'` и `systemctl status` на предмет `Killed`/`signal=KILL`.
- Сохранять «предсмертный» хвост TUI: при рестарте копировать последний `session_current.txt` в crash-архив (по `ExecStopPost`).

### Наиболее вероятные причины (по коду) и фиксы

**1. Orphan-watchdog по смене `ppid` (ложное срабатывание).**
```ts
// /opt/workspace/scripts/telegram-plugin/server.ts (фрагмент, строки ~1659-1666)
const bootPpid = process.ppid
setInterval(() => {
  const orphaned =
    (process.platform !== 'win32' && process.ppid !== bootPpid) ||
    process.stdin.destroyed ||
    process.stdin.readableEnded
  if (orphaned) shutdown()
}, 5000).unref()
```
При reparenting (tmux/bun-обёртка/двойной fork) `ppid` может легитимно измениться → плагин считает себя сиротой и сам себя гасит → канал падает. Плагин **не патчим**, поэтому **лечим рекавери**: watchdog (см. Проблему A) замечает мёртвый `bot.pid` и делает `systemctl restart`. То есть этот класс отвалов закрывается тем же supervisor'ом автоматически, без правок плагина.

**2. Лимит seat (Anthropic Team, per-user) → выход Claude → рестарт.**
Плагин сам детектит такие состояния (строки 680-691): `usage limit reached`, `5-hour limit`, `rate-limit`, `credit balance`. Подписка — Team, и каждый пользователь работает под **своим seat** (свой `credentials.json`), поэтому лимит — это исчерпание скользящего/недельного окна **конкретного seat**, а не общего пула. При исчерпании Claude завершает сессию → `systemd` рестартит → у пользователя «бот перезагрузился». Плагин уже **детектит** эти состояния и предупреждает пользователя (не убивает) — сам выход инициирует `claude`, без патча `claude` это поведение не меняем. **Интерим:** supervisor поднимает сервис, каждый такой рестарт логируется как «лимит seat» (объяснимый, не «случайный»). **Системный фикс:** доступ за LiteLLM-гейтвеем с очередью/троттлингом и деградацией вместо падения (сборка — [08](08-runtime-and-gateways.md)) — устраняет саму причину. Этот фикс висит на маршруте OAuth-seat→LiteLLM, который **сначала доказывается блокирующим спайком до M2** (см. [08](08-runtime-and-gateways.md)); при провале применяется fallback-прокси.

**3. OOM (нет лимитов памяти в unit).**
В [`claude-tg@.service`](/opt/workspace/scripts/claude-tg@.service) нет `MemoryMax/MemoryHigh`. Тяжёлая сессия/утечка → ядро убивает процесс → рестарт. **Фикс:** добавить `MemoryHigh=` (мягкий троттлинг) и `MemoryMax=` (потолок), `OOMPolicy=continue`; включить аккаунтинг (`MemoryAccounting=true`) для диагностики. Это же — основа эластичных лимитов целевой изоляции (см. [08](08-runtime-and-gateways.md)).

**4. Рестарт-петля при коротком сбое.**
`RestartSec=20` + `StartLimitBurst=10/300s`: серия мелких сбоев может выглядеть как «случайные перезагрузки» и в пределе упереться в лимит старта. **Фикс:** после устранения причин 1-3 — поднять `RestartSec` с экспоненциальной паузой и убедиться, что рестарты стали редкими; логировать каждый рестарт в аудит.

### Порядок действий по B
1. Включить инструментацию (journald, exit-code, OOM-проба, crash-хвост).
2. Поднять watchdog-supervisor (из Проблемы A) — он же закрывает рекавери для #1 без патча плагина.
3. Добавить лимиты памяти + аккаунтинг (#3).
4. Смягчить эффект лимитов подписки (#2): на интериме — наблюдение/уведомление через supervisor; системно — LiteLLM-гейтвей с очередью.
5. Понаблюдать NRestarts; при остаточных рестартах — разбирать по собранным логам.

## Критерий выхода из Фазы 0
- `claude -p` (и любые дочерние запуски `claude`) **по построению** не затрагивают TG-канал (Уровень 1); watchdog-страховка поднимает поллер за ≤30 с при любом ином отвале (Уровень 2).
- Частота рестартов сведена к редким и **объяснимым** (каждый рестарт виден в логах с кодом/причиной).
- Память лимитирована, OOM-смертей нет.
- Секреты помечены к ротации (выполняется в Фазе секретов, [04](04-secrets-and-data-migration.md)).

Только после этого начинается архитектурная миграция ([02-strategy-and-phases.md](02-strategy-and-phases.md)).
