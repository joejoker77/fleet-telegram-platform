vault 4. Да» — все 4 вопроса ниже решены в пользу рекомендаций) →
**ПОСТРОЕНО 2026-06-11** → **ЗАДЕПЛОЕНО + ПРИЁМКА OK 2026-06-11 ~10:20**
(оператор: m5.5b-secretd.sh, m1.5 re-run, m5.5b-accept.mjs → «acceptance: OK»).

Дополнение при сборке (за пределами вопросов 1–4): deny-путь (`onReject`)
удаляет staged-секрет только если он НЕ привязан (`onlyIfUnbound`) — иначе
параллельный same-name approve, уже привязавший секрет, терял бы его от

([M5.5-mcp-gate-design.md](M5.5-mcp-gate-design.md)): тот же флоу
scan → approval → apply, плюс секрет.

Источники требований: [04](04-secrets-and-data-migration.md) (инвариант:
секреты ТОЛЬКО в OneCLI, в файлах — заполнители; подмена на egress),
[11](11-integrations.md) («ключи уходят в OneCLI»), ADR-002 (egress =
proxy-only, БЕЗ host-whitelist), M5.4b (механизм аппрувов).

## Сужение скоупа против анонса в M5.5

M5.5 обещал в M5.5b два пункта: (а) интейк секретов, (б) «канал добавления
хостов в egress-allowlist». Пункт (б) **выпадает**: по ADR-002 (принят
Vitaliy 2026-06-08) у прокси НЕТ host-allowlist — egress default-allow
pass-through через единый аудируемый чокпойнт. Remote-MCP на новый хост
уже работает без какой-либо привилегированной операции (проверено живьём:
via-proxy запросы к произвольным хостам проходят, это by-design). Фраза
про allowlist в M5.5-доке была ошибкой против ADR-002.

Остаётся ровно одно: **MCP, которым нужен API-ключ.**

## Модель (та же, что у composio/exa и старого deploy-mcp)

Секрет живёт в OneCLI vault, привязан к агенту `vitaliy-bot` с
`host-pattern` + `header-name` + `value-format`. В файлах песочницы —
заполнитель `${SECRET:имя}`. Когда MCP-процесс (или удалённый MCP-клиент)
делает HTTPS-запрос через прокси и хост совпадает с pattern — прокси
подставляет заголовок. Под значение **никогда не видит**.

Покрывается: remote-MCP с header-auth и stdio-MCP, чья аутентификация —
HTTP-заголовок к конкретному хосту (прокси перезапишет заголовок с
заполнителем на настоящий). НЕ покрывается (осознанно, по инварианту):
MCP, которым нужен сырой ключ локально — подпись запросов (AWS sigv4),
не-HTTP протоколы. Это честно показывается в Mini App.

## Поток

```
Mini App McpBuilder, секция «🔑 Секрет» (опциональная):
  значение ключа + host-pattern + имя заголовка + формат значения
  (пресеты: Bearer {value} / {value} / Basic {value}; X-API-Key и т.п.)
  В стансе вместо значения — заполнитель ${SECRET:vitaliy-mcp-<name>}.
  → POST /mcp/connect { name, stanza, secretSpec? }   (JWT, HTTPS)
      1. shape-валидация стансы (M5.5) — инлайн-секреты по-прежнему отказ;
         secretSpec.value валидируется отдельно (непустой, ≤4KiB)
      2. скан стансы (M5.5, значение секрета в скан НЕ попадает)
      3. pass → cp-secretd: stage_secret (создать в vault БЕЗ привязки —
         непривязанный секрет инертен, его никто не может использовать)
      4. createApproval(kind:"mcp.connect", payload: станса + secretMeta
         {name, hostPattern, headerName, valueFormat} — БЕЗ значения)
  → карточка аппрува показывает вердикт сканера + строку
    «🔑 секрет → <host-pattern>, заголовок <header>»
  → allow → applier (M5.5) ДОПОЛНИТЕЛЬНО: cp-secretd bind_secret
    (аддитивно, с верификацией пред-состояния — паттерн git-pat-vault.sh),
    затем обычный apply стансы (.mcp.json + enabledMcpjsonServers + commit)
  → deny / expire → cp-secretd delete_secret (best-effort; непривязанный
    секрет и так инертен, lazy-чистка при следующем list/connect)
disconnect (без аппрува, как в M5.5) → снять стансу + unbind+delete
    секрета этого MCP (имя связано конвенцией vitaliy-mcp-<name>)
```

Значение секрета **нигде не персистится вне vault**: не в PG (payload
аппрува), не в Redis, не в логах, не в audit-записях. Между connect и
approve оно уже в vault (staged, unbound) — cp-api его в памяти не держит.

## Привилегированный канал cp-api → OneCLI: `cp-secretd`

Проблема: `onecli` CLI требует root на хосте + `HOME=/root` (ключ админа).
cp-api — контейнер. Дать ему админ-ключ OneCLI = компрометация cp-api
раскрывает ВЕСЬ vault всех агентов. Неприемлемо.

Решение — **узкий root-хелпер на unix-сокете** (паттерн audit-collector):

- `cp-secretd` — маленький bash/python на хосте, systemd
  **socket-activated** (`cp-secretd.socket` → `cp-secretd@.service`,
  процесса нет, пока никто не подключился; НЕ таймер, НЕ поллер, ноль LLM).
- Сокет `/run/cp-secretd/secretd.sock`, root:cp-secret 0660; каталог
  бинд-монтируется в cp-api (как cp-audit-run).
- JSON-запрос/ответ, четыре глагола: `stage_secret` (create unbound,
  rotate-если-существует-и-не-привязан), `bind_secret` (аддитивно +
  verify-after-set + откат пред-состояния при потере привязок — дословно
  логика git-pat-vault.sh), `delete_secret` (unbind+delete),
  `secret_exists`.
- **Зашитые в хелпер инварианты** (не параметры): имя обязано матчить
  `^vitaliy-mcp-[a-z0-9][a-z0-9._-]{0,48}$`; агент — только `vitaliy-bot`;
  значения никогда не возвращаются, не логируются, не попадают в audit;
  `Environment=HOME=/root` в юните (инцидент 2026-05-29).
- Каждый вызов хелпер дублирует в audit-сокет: `mcp.secret.staged/bound/
  deleted` (имя+host-pattern, без значения).
- Известное ограничение: `onecli secrets create --value` на argv ~1с виден
  в /proc root-процесса — то же принятое окно, что у git-pat-vault.sh и
  mcp-set-secret.

Отвергнутая альтернатива: scoped-токен OneCLI в podman-секрете cp-api —
у OneCLI нет скоупов токенов («только secrets.create + bind своего
агента» выразить нечем), получился бы полный админ-ключ в контейнере.

## Затрагиваемое

- **Хост (новое, в teardown-лист):** `runtime/install/m5.5b-secretd.sh`
  (ставит хелпер + socket-юнит + группу; идемпотентный) и
  `m5.5b-secretd-rollback.sh` (одна команда: stop+disable+rm — до запуска
  установки, правило rollback-first).
- cp-api: `mcp-gate.ts` (+secretSpec валидация, stage/bind/delete через
  сокет-клиент), `mcp-routes.ts` (+secretSpec в connect), applier в
  `index.ts` (+bind перед apply); m1.5 — бинд-монт сокет-каталога.
- Mini App: секция «🔑 Секрет» в McpBuilder (+ честная подсказка, какие
  MCP покрываются), пометка 🔑 в списке подключённых.
- Приёмка `install/m5.5b-accept.mjs`: connect с секретом → staged unbound →
  allow → bound (проверка `onecli agents secrets`) + станса с заполнителем
  → deny-ветка → секрет удалён → disconnect → unbind+delete. Плюс
  негатив: имя вне конвенции → отказ хелпера.

## Откат

- Канал целиком: `m5.5b-secretd-rollback.sh` (юниты+сокет+группа) +
  `git revert` + re-run m1.5. Vault-состояние скрипт не трогает.
- Конкретный секрет: disconnect (= unbind+delete); вручную —
  `onecli agents set-secrets` на пред-состояние + `secrets delete`.

## Вопросы на согласование

1. **Канал**: root-хелпер `cp-secretd` на socket-activation (рекомендую)
   — против админ-ключа OneCLI внутрь cp-api. Влияет на blast-radius:
   с хелпером компрометация cp-api даёт максимум «создать/привязать секрет
   к vitaliy-bot», а не прочитать весь vault.
2. **Подтвердить выпадение «egress-allowlist канала»** из скоупа — по
   твоему же ADR-002 он не нужен (прокси default-allow). Если когда-то
   захочется душить конкретные хосты — это `onecli rules --action block`,
   отдельная ручная операция.
3. **Стейджинг значения**: сразу в vault unbound (рекомендую: значение
   нигде кроме vault не лежит, переживает рестарт cp-api) — против
   держать в памяти cp-api до approve (проще, но рестарт = «введи заново»
   и значение живёт в heap process'а).
4. **Ротация ключа** существующего MCP: тем же connect-overwrite флоу
   (M5.5 №4), stage_secret перезаписывает непривязанный/привязанный своему
   же имени секрет — да?
