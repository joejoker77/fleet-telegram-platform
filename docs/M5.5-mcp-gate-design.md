## Поток (целиком из Telegram, без операторских шагов)

```
Mini App McpBuilder (форма: name, stdio|http, command+args | url,
                     env/headers, timeout; raw-JSON вид как в других билдерах)
  → POST /mcp/connect (cp-api, JWT)
      1. shape-валидация стансы (только разрешённые ключи, name-regex)
      2. скан: scanArtifact(kind:"mcp") — детерминированный (builtin+YARA)
         → judge (:8090, событийный, fail-closed). verdict != pass → отказ,
         вердикт показывается в Mini App (ScanResults), НИЧЕГО не записано.
      3. pass → createApproval(kind:"mcp.connect",
         payload:{stanza, verdict, findings}) → уведомление в чат (M5.4b)
  → пользователь видит вердикт сканера ВНУТРИ карточки аппрува и жмёт ✅/❌
  → обработчик ответа (POST /approvals/:id/answer): если allowed и
    kind=mcp.connect → applyMcpStanza() СИНХРОННО в том же запросе
      a. merge стансы в /home/<tenant>/work/.mcp.json (mcpServers)
      b. append имени в enabledMcpjsonServers в ~/.claude/settings.json
      c. commit settings.json в git HEAD ~/.claude (владелец файлов — tenant uid)
      d. audit: mcp.connect.applied (или .apply_failed → видно в Mini App)
  → denied / expired (ttl 600 c, lazy, fail-closed) → ничего не записано
```

Никаких новых контейнеров, юнитов, таймеров, миграций БД (таблица approvals уже
есть). Никаких рекуррентных LLM-вызовов: judge дёргается один раз на клик
пользователя. cp-api уже имеет всё нужное: `/home/<tenant>` смонтирован (m1.5,
canonical), `@fleet/scanners` слинкован (preflight m1.5), judge на 127.0.0.1:8090
доступен (host network), approvals-механизм живой (acceptance OK).

## Решения и их мотивировка

1. **Куда пишем**: `work/.mcp.json` + `enabledMcpjsonServers` — как велит
   [10] и как уже живут composio/exa. НЕ в `settings.json#mcpServers` (это
   legacy-канал deploy-mcp). WP7 settings-guard пропускает оба ключа
   (enforce только permissions+hooks) → rebaseline НЕ нужен. Коммит в git
   HEAD `~/.claude` — чтобы restore-from-HEAD легаси-гейта не съел запись.
2. **Apply в обработчике ответа**, а не в фоновом waitForAnswer: ноль
   фоновых ожидателей, переживает рестарт cp-api, детерминированно, быстро
   (две записи файлов). waitForAnswer остаётся для будущих блокирующих
   клиентов.
3. **Вердикт сканера едет в payload аппрува** — человек подтверждает,
   глядя на вердикт, а не вслепую (gate at untrusted entry + inline
   approval, без файловых белых списков, которые из Telegram не заполнить).
4. **Inline-секреты в стансе — отказ в v1** (см. ниже). Детерминированный
   сканер и так флагует secret-in-env; cp-api дополнительно отклоняет
   env/headers-значения токеновидной формы с понятным сообщением. Инвариант
   «секреты только в OneCLI, в файлах — заполнители» не нарушаем ни разу.
5. **Отключение MCP — без аппрува**: кнопка disconnect в Mini App убирает
   стансу из обоих файлов + audit. Снятие capability — безопасное
   направление; это же и есть однокомандный откат подключения.
6. **Вступает в силу со следующей сессии** Claude Code (конфиг читается на
   старте) — честно пишем это в Mini App после apply. Рестарт пода не нужен
   и не делается.

## Чего НЕТ в v1 (кандидат на M5.5b, отдельный дизайн)

- **MCP с секретами**: интейк ключа из Mini App → секрет в OneCLI + бинд к
  `<tenant>-bot` + host-pattern → в стансе заполнитель. Требует
  привилегированного канала cp-api → OneCLI admin API (предложение: scoped
  токен «только secrets.create + bind к своему агенту» в podman-секрете).
- **Remote (url) MCP на новый хост**: нужен пункт в egress-allowlist прокси
  (ADR-002) — та же привилегированная операция, та же M5.5b.
- v1 покрывает: stdio-MCP без секретов (npx-пакеты и локальные бинари) и
  remote-MCP на уже разрешённые хосты.
- Проверить на живой системе: проходит ли `npx` fetch к registry.npmjs.org
  через прокси из пода (ожидаемо да — хост в базовом allowlist).

## Затрагиваемые файлы (всё в репо, ничего на хосте)

- cp-api: `apps/api/src/mcp-routes.ts` (connect/disconnect/list),
  `mcp-apply.ts` (merge/commit, fs-safety-конфайнмент путей), хук в
  `approval-routes.ts` (kind=mcp.connect → apply).
- Mini App: `components/McpBuilder.tsx` (+ инлайн ScanResults), пункт меню.
- Без изменений: `@fleet/scanners`, `approvals.ts` (generic), схема БД.

## Откат

- Фича целиком в коде cp-api/miniapp: live-откат = git revert + перезапуск
  m1.5 (контейнеры исполняют рабочее дерево).
- Откат конкретного подключения = disconnect-endpoint; вручную: убрать ключ
  из `work/.mcp.json` и из `enabledMcpjsonServers` (jq-однострочник будет в
  доке деплоя).
- Записи только в два tenant-файла; никаких изменений хост-конфигурации →
  отдельный rollback-скрипт на сервере не требуется (правило
  rollback-first соблюдено самой архитектурой apply).

## Реализация (построено 2026-06-11)

- cp-api: `apps/api/src/mcp-gate.ts` (валидация + отказ inline-секретам,
  скан, apply/disconnect, best-effort git commit settings.json ОТ UID
  ТЕНАНТА), `mcp-routes.ts` (GET /mcp/list, POST /mcp/connect, POST
  /mcp/disconnect), `approval-routes.ts` — параметр `appliers` (kind →
  синхронный apply в обработчике ответа), `config.ts` — `JUDGE_URL`
  (дефолт `http://127.0.0.1:8090`).
- Mini App: `components/McpBuilder.tsx` (форма stdio/remote, JSON-превью,
  список подключённых + disconnect, инлайн-вердикт), пункт «🔌 Подключить
  MCP», `api.ts` — mcpList/mcpConnectRaw/mcpDisconnect.
- `install/m1.5-services.sh`: бутстрап `apk add git` в cp-api (node:alpine
  без git; нужен для коммита settings.json в git HEAD тенанта).
- Приёмка: `install/m5.5-accept.mjs` (list / inline-секрет→400 /
  curl|sh→422 deterministic / allow→applied→в списке / deny→не применён /
  disconnect→исчез). Шаги 4–5 шлют реальные уведомления пилоту.
