# M5.9 — WorkflowBuilder: конструктор воркфлоу в Mini App

Закрывает пункт «WorkflowBuilder → граф из субагентов/скиллов → компиляция в
`commands/`+`agents/`» ([10-authoring-miniapp-ide](../../upgrade/10-authoring-miniapp-ide.md)
L17, модель композиции — [12-artifacts-sharing](../../upgrade/12-artifacts-sharing.md)
«Workflow — нативная композиция»). Pilot: vitaliy only (как весь M1+).

## Модель (из дока 12, без изменений)

У Claude Code нет примитива «workflow» — это наш конструкт поверх нативных:
**workflow = оркестрирующая slash-команда** (`~/.claude/commands/<name>.md`),
которая по шагам вызывает субагентов (Task tool) и скиллы (Skill tool).
Никакого рантайма, планировщика или нового формата — компилируем в точные
байты нативного файла, который Claude Code исполняет сам. Портируемо,
понятно сканерам, шарится через GitHub как есть (M8).

## Скоуп MVP — три сужения против дока 12

1. **Линейная последовательность, не граф.** Slash-команда исполняется
   одним оркестратором сверху вниз — честная модель MVP это упорядоченные
   шаги. Параллельные ветки/связи = M8 (вместе с серверным компилятором).
   UI: список шагов с ↑/↓/✕, не canvas с рёбрами.
2. **Шаги ссылаются на СУЩЕСТВУЮЩИХ субагентов и скиллы.** Новый субагент
   создаётся соседним SubagentBuilder (уже есть) — WorkflowBuilder не
   дублирует его форму. Поэтому компилируем ТОЛЬКО `commands/<name>.md`;
   `agents/*.md` из формулы дока 10 уже покрыты существующим билдером.
3. **Компиляция на клиенте**, как у Subagent/CommandBuilder
   (`builders/compile.ts` + обязательный raw view в BuilderShell).
   `POST /build/workflow` из дока 12 — серверный компилятор для
   маркетплейса/провенанса — остаётся в M8, на MVP он дал бы тот же
   текст файла ценой нового эндпоинта.

**Следствие: ноль новых поверхностей.** Ни нового маршрута cp-api, ни
изменений пода/образа. Список доступных субагентов и скиллов Mini App уже
видит через `GET /fs/tree` (`agents/*.md`, `skills/*/SKILL.md` — внутри
песочницы `.claude`); сохранение — существующий `PUT /fs/file` со
сканер-гейтом (M5.5-класс) и аудитом `fs.put`. Деплой = копия dist, всё.

## UI (экран WorkflowBuilder, вход из меню билдеров)

Форма (BuilderShell: форма + raw view + save):

- **Имя** (kebab-case, общий `validateName`) → `commands/<имя>.md`.
- **Description** + **argument-hint** (что передаётся воркфлоу при вызове,
  доступно в теле как `$ARGUMENTS`).
- **Шаги** (упорядоченный список, ↑/↓/✕, минимум 1):
  - тип шага: **субагент** (пикер из `agents/*.md` песочницы) /
    **скилл** (пикер из `skills/*/SKILL.md`) / **инструкция** (свободный
    текст для самого оркестратора — клей между делегациями);
  - **задача шага** — текст, что субагенту/скиллу делать; подсказка
    «результат предыдущего шага у оркестратора в контексте — ссылайся
    на него словами».
- Пустые пикеры (нет ни одного субагента/скилла) — шаг этого типа
  недоступен с подсказкой «создай в SubagentBuilder».

## Компилятор (`compileWorkflow` в `builders/compile.ts`)

Детерминированный текст, видимый в raw view байт-в-байт:

```markdown
---
description: <description>
argument-hint: <argument-hint>
---

Ты — оркестратор воркфлоу «<имя>». Вход: $ARGUMENTS
Выполни шаги строго по порядку; результат каждого шага используй в следующих.

## Шаг 1 — субагент: research
Запусти субагента `research` (Task tool, subagent_type=research) с задачей:
<задача шага>

## Шаг 2 — скилл: web-research
Выполни скилл `web-research` (Skill tool):
<задача шага>

## Шаг 3 — инструкция
<текст инструкции>

В конце сведи результаты шагов в один ответ пользователю.
```

Валидации формы: имя (regex/длина/коллизия пути — уже в BuilderShell),
≥1 шаг, у каждого шага непустая задача/текст, ссылки шагов указывают на
существующие файлы (по `existingPaths` из fs/tree).

## Ограничение, найденное на приёмке (2026-06-12, /fact-quest)

Реестр субагентов Claude Code читается при СТАРТЕ сессии: субагент, созданный
билдером после запуска текущего claude, не виден его Task tool до перезапуска
(switch сессии в Mini App / рестарт пода) — Task падает с «Agent type not
found». Оркестратор-бот при этом не слеп: он читает `agents/<name>.md` и может
выполнить шаг тем же системным промптом через general-purpose (так и прошла
приёмка). Это ограничение Claude Code, не билдера. TODO (мелочь, не блокер):
после сохранения субагента показывать в UI «станет доступен как subagent_type
после перезапуска сессии».

## Безопасность / инварианты

- Тот же траст-класс, что остальные билдеры: тенант правит СВОЮ песочницу
  `.claude` руками через детерминированную форму; LLM в цепочке нет.
- `PUT /fs/file` уже гонит контент через сканер-гейт до записи + аудит —
  ничего нового не добавляем и не ослабляем.
- Воркфлоу не получает новых привилегий: субагенты/скиллы, которые он
  вызывает, уже установлены и уже прошли свои гейты (CI репо скиллов,
  M5.5 для MCP); команда лишь компонует их.
- Нулевые рекуррентные процессы: воркфлоу запускается только пользователем
  (`/<имя>` в чате) — таймеров/cron/LLM-по-расписанию нет.
- Rollback: убрать экран из Mini App (revert + dist copy); скомпилированные
  `commands/*.md` — обычные файлы тенанта, инертны, удаляются через
  FileTree/IDE.

## Деплой / приёмка

1. Деплой: vite build + `cp -a …/apps/miniapp/dist/. /var/www/miniapp/dist/`
   (cp-api и под НЕ трогаем).
2. Приёмка (ручная, скрипт не нужен — серверной логики нет):
   - создать в билдере воркфлоу из 2 шагов (субагент + скилл), raw view
     совпадает с ожидаемым текстом, save проходит сканер;
   - файл виден в FileTree и в IDE;
   - вызвать `/<имя> <аргумент>` в чате бота — оркестратор прошёл шаги
     по порядку (видно в LiveActivity);
   - невалидные кейсы: имя-коллизия, 0 шагов, пустая задача — save
     заблокирован с причиной.
