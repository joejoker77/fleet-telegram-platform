## Что уже есть (ground truth)

- Образ `claude-user` несёт code-server (Containerfile:26), entrypoint
  стартует его на `127.0.0.1:8443 --auth none` — изнутри netns пода,
  снаружи недоступен вовсе. Терминал в нём = терминал пода: tenant-uid,
  RO rootfs, cap-drop ALL, shellfirm, egress только через OneCLI-прокси,
  `claude` CLI на месте. Т.е. браузерный терминал не добавляет НИ ОДНОЙ
  новой способности сверх того, что под уже имеет.
- Хост-прокси — **nginx** (vhost miniapp уже живёт так); DNS — CF-проксируемый
  wildcard → новое имя резолвится без новых записей.
- cp-api умеет JWT-сессии (Redis) и аудит.

## Два отклонения от upgrade/10 (и почему)

1. **nginx `auth_request` вместо Caddy forward-auth.** Хост уже держит
   nginx с vhost'ами и certbot; `auth_request` — тот же forward-auth
   паттерн 1-в-1. Ставить Caddy = второй reverse-proxy на той же машине
   ради синонимичной директивы. Не плодим компонент.
2. **Поддомен `ide.ai-assistant.gg` вместо пути `/<user>/ide`.**
   code-server под сабпутём требует rewrite-хаков и периодически ломается
   (websocket/asset paths); поддомен — официально поддерживаемый режим.
   Wildcard DNS уже есть. Мульти-тенант потом: `<user>-ide.…` тем же
   шаблоном vhost (auth-эндпоинт сверяет тенанта по Host) — для пилота
   один vhost = vitaliy.

## Архитектура

```
браузер ──https──> CF ──> nginx (ide.ai-assistant.gg)
                            │  каждый запрос: auth_request → cp-api GET /ide/auth (cookie)
                            └─ proxy_pass → unix:/run/cp-ide/vitaliy/ide.sock (code-server)
вход:  Mini App «🖥 IDE» → POST /ide/ticket (JWT) → одноразовый тикет (Redis, 60 c)
       → браузер открывает /api/ide/login?t=… → cp-api ставит cookie (Redis-сессия) → redirect /
```

**code-server переезжает с tcp на unix-socket** (`--socket`): сокет в
бинд-маунте `/run/cp-ide/<user>` → в сеть не выставлен вообще (ни в
cl-net, ни на хост-порты), соседний под физически не дотянется; nginx
ходит в сокет напрямую, минуя netns пода. `--auth none` остаётся —
инвариант: ЕДИНСТВЕННЫЙ путь к сокету это nginx, и каждый запрос
(включая websocket upgrade) проходит `auth_request`.

## Компоненты

1. **entrypoint.sh** (образ): если задан `CP_IDE_SOCKET` — `code-server
   --socket "$CP_IDE_SOCKET" --socket-mode 0660 --auth none`, иначе
   как сейчас (обратная совместимость: без переменной ничего не меняется).
   → пересборка m2.1 (слои кэшированы, быстро) + рестарт пода —
   **в конце сессии**, вместе с уже запланированным рестартом хвоста M4.
2. **claude-pod-run**: `install -d` хост-дира `/run/cp-ide/$U`
   (tenant-uid : gid www-data, 0750), `-v` его в под, `-e CP_IDE_SOCKET`.
   Условно (как cl-net/audit): нет дира www-data — поведение прежнее.
3. **cp-api** (3 эндпоинта, всё в Redis, без новых привилегий/каналов):
   - `POST /ide/ticket` (Bearer JWT) → `{url}` c одноразовым `t`
     (GETDEL, TTL 60 c). Аудит `ide.ticket`.
   - `GET /ide/login?t=…` → проверка тикета → cookie `cp_ide`
     (HttpOnly, Secure, SameSite=Lax; Redis-сессия TTL 12 ч) → 302 `/`.
     Аудит `ide.login`.
   - `GET /ide/auth` (internal, для auth_request) → 204/401 по cookie +
     сверка osUsername тенанта с vhost'ом. Без аудита (per-request шум);
     неуспехи видны в nginx-логе.
4. **nginx vhost** `deploy/nginx-ide.conf` (шаблон в репо, оператор
   ставит как miniapp-вариант + certbot): `/api/ide/*` → cp-api;
   `location /` → `auth_request` + `proxy_pass http://unix:…ide.sock`
   + websocket upgrade + `Cache-Control: no-cache` урок M5.5b не нужен
   (code-server сам версионирует), но заголовки upgrade обязательны.
5. **Mini App**: кнопка «🖥 IDE» (экран дерева) → `POST /ide/ticket` →
   `openLink(url)` (внешний браузер; в webview Telegram IDE неюзабелен).
6. **Приёмка** `install/m5.6-accept.mjs`: тикет→login→cookie→200 от
   code-server через nginx; повторный тикет → 401 (одноразовость);
   без cookie → 401; чужой/протухший тикет → 401.
7. **Откат** `install/m5.6-rollback.sh` (готовится ДО деплоя): снять
   vhost + удалить /run/cp-ide — под продолжает работать как сегодня
   (code-server вернётся на 127.0.0.1:8443 после рестарта без env).

## Безопасность

- Терминал в браузере = возможности пода, не больше (см. ground truth).
  Периметр (shellfirm/egress/RO rootfs/no sudo) уже стоит — это и есть
  модель «даём способность, ограничиваем blast radius».
- Сокет вне сети; cookie HttpOnly+Secure; тикет одноразовый 60 с; TLS
  через CF + origin-cert (как miniapp).
- cp-api НЕ получает доступа к сокету IDE — он только аутентифицирует.
