## 1. Цель и критерий «готово»
Тенант может **опубликовать** свой артефакт (`.claude/`-файлы) в общий реестр и **импортировать**
чужой — детерминированно, с обязательными сканами и неизменяемым аудитом, без того чтобы
пользователь сам пушил в Git. Гейт M8 (из doc 06/12):
- workflow из билдера компилируется в валидные `commands/`+`agents/` (✅ уже умеем — M5.9);
- публикация без pass сканеров невозможна; PR создаёт агент; провенанс в реестре;
- импорт делает повторный скан и ставит **зафиксированную версию**; fail → отказ с причиной;
- все вердикты — в append-only аудите.

## 3. Scope MVP (намеренно срезаю риск)
- **Типы артефактов MVP:** `skill`, `subagent`, `command`, `workflow` — чистые файлы, низший риск,
  покрыты Skill Scanner + deterministic. `mcp` — импорт MCP УЖЕ закрыт существующим mcp-gate
  (M5.5), в маркетплейс заводим его шарингом записи `.mcp.json` ПОЗЖЕ. `plugin` — **DEFER**
  (highest-risk: все три сканера + AgentShield; отдельный под-этап M8.3).
- **Видимость MVP:** `public` + `private` (selective/«поделиться выборочно» — позже; колонка уже есть).
- **Хранилище MVP:** GitHub-org репозиторий = source of truth артефактов (`git_ref` в
  `artifact_versions`). **MinIO/объектное зеркало — DEFER** (2 тенанта, GitHub достаточно; зеркало
  нужно для масштаба/доступности, заводим в M10/при росте).
- **Пилот:** только vitaliy + dmrudenko. Флаг тенанта гейтит фичу (как все M5/M6).

## 4. GitHub-org как стор + агентский PR (net-new #1)
- Одна **общая приватная org** для флота (предлагаю отдельную от `joejoker77/claude-bot-skills`,
  т.к. та — для bootstrap-скиллов фермы; артефакты тенантов — другой trust-домен). Рабочее имя:
  `fleet-artifacts` (1 репо, дерево `artifacts/<type>/<owner>/<name>/` + версии = git-теги/коммиты).
- **Платформенный GitHub-org PAT — секрет в OneCLI** (НЕ в файле), bound к агенту `cp-registry-bot`
  (новый OneCLI-агент control-plane-side, по аналогии с queued `cp-judge-bot`). cp-api ходит в
  api.github.com через OneCLI-прокси → прокси инжектит `Authorization: Bearer <PAT>`. Это
  расширяет git-pat-vault-паттерн с «под пушит свой репо» на «cp-api пушит org-репо».
- **PR создаёт и мёржит сам агент** (не пользователь): cp-api после scan-pass коммитит файлы в
  ветку, открывает PR, (опц.) ревью-комментарий, мёржит. Провенанс (автор-тенант, версия,
  scan-вердикты, git-sha) → `artifact_versions.provenance` (jsonb) + `git_ref`.

## 5. Модель данных — дельта
Таблицы есть. Нужна **миграция 0003** только для недостающих полей/связи:
- `artifacts`: + `description text`, + уникальный индекс `(owner_user_id, type, name)`.
- `artifact_versions`: + `status` (enum `draft|scanning|published|rejected`), + `scan_summary jsonb`.
- (опц.) `selective_grants` — отложено вместе с visibility=selective.
Никаких ломающих изменений; `installs.pinned_version` уже есть для пиннинга импорта.

## 6. API (роуты в cp-api — консистентно с sessions/mcp/approvals)
> doc 06 рисует отдельный `apps/registry`; для MVP на 2 тенанта это лишний процесс — делаю
> `registry-routes.ts` в cp-api, с прицелом на безболезненную экстракцию в свой сервис на M10.

```
GET  /registry/items?type=&visibility=          # каталог (мои + public)
GET  /registry/items/:id                         # карточка + версии + последние scan_results
POST /registry/publish    { artifactPath, type, name, version, visibility }
                                                 # → scanArtifact → judge → approval → agentPR → запись версии
POST /registry/import     { artifactVersionId }  # → ПОВТОРНЫЙ scanArtifact → approval → установка в .claude/
DELETE /registry/items/:id                        # снять с публикации (только owner; installs не трогаем)
```
Все мутации → audit (`registry.publish|import|reject`), вердикты → `scan_results`, через тот же
`tenantHome`-резолвинг, что и mcp-gate (мультибот-safe).

## 7. Поток ПУБЛИКАЦИИ (детерминированно, fail-closed)
1. Mini App: тенант выбирает артефакт (scoped FileTree, scope=project/artifacts) → «Опубликовать»
   → `POST /registry/publish`.
2. cp-api читает файлы артефакта из песочницы тенанта (`tenantHome/.claude/...` или `~/work`),
   нормализует в `ScanInput`, зовёт `scanArtifact` (deterministic → judge через Orchestrator,
   **worst-verdict-wins, fail/error → стоп + причина**). Вердикты → `scan_results`.
3. Pass → создаётся **approval-карточка** (M5.4b): «Опубликовать `<name>` v`<x>` как `<public|private>`?»
   — Telegram-нотификация токеном тенанта + ответ в Mini App. (Само-публикация своего же артефакта:
   approval опционален — открытый вопрос Q3.)
4. Allow → агент (cp-api под `cp-registry-bot` PAT) коммитит файлы в `fleet-artifacts`, открывает+мёржит
   PR, пишет `artifact_versions` (version, git_ref=sha, provenance, status=published). Audit.
5. Fail/Deny → `status=rejected` + причина в карточке; ничего не публикуется.

## 8. Поток ИМПОРТА (повторный скан — каждый импорт пересекает границу доверия)
1. Mini App «Маркетплейс» → выбор версии → `POST /registry/import`.
2. cp-api тянет **зафиксированную версию** из GitHub-org (по git_ref).
3. **ПОВТОРНЫЙ `scanArtifact`** под актуальные правила (ruleset мог измениться с публикации;
   judge-кэш по hash+ruleset+model сам решит hit/miss). Fail/error → отказ + причина, **ничего не ставим**.
4. Pass → approval-карточка «Импортировать в свою песочницу?» → allow → файлы пишутся в `.claude/`
   тенанта (skill→`skills/<name>/`, subagent→`agents/<name>.md`, command→`commands/<name>.md`,
   workflow→`commands/`+`agents/`), запись `installs` (pinned_version). Audit `registry.import`.
5. Конфликт имён — two-tap «перезаписать?» (как M5.5 overwrite). Платформенные скиллы/хуки —
   защищены, импорт их не перетирает (AgentShield-залок).

## 9. Безопасность / инварианты
- **LLM только событийно** (publish/import) — НЕ рекуррентно ([[feedback_no_recurring_llm_calls]]);
  judge — только через Orchestrator (кэш/single-pass/$-cap), без прямых вызовов сканеров.
- **Секреты только OneCLI**: org-PAT bound к `cp-registry-bot`, инжект на прокси; в БД/логах/аудите —
  никогда не значение.
- **Fail-closed везде**: judge-error == block (и публикации, и импорта).
- **Аудит append-only** на каждое решение (publish/import/reject/scan-verdict).
- **Граница доверия = импорт**: повторный скан обязателен, даже если на публикации был pass.
- **Пилот-only** ([[feedback_rearchitecture_pilot_vitaliy_only]]): фича за флагом тенанта; остальные боты не трогаем.

## 12. Порядок сборки (после approve)
1. Миграция 0003 + расширение схемы.
2. GitHub-org `fleet-artifacts` + `cp-registry-bot` OneCLI-агент + org-PAT в vault (operator-step).
3. `registry-routes.ts` + publish-поток (scan→judge→approval→agentPR) + reuse approvals.
4. Import-поток (pull→re-scan→approval→install).
5. Mini App: Маркетплейс + «Опубликовать» + карточки.
6. `m8.1-accept.mjs` (e2e: publish skill → scan-pass → PR → import в «другого» → re-scan → install;
   + negative: артефакт с инъекцией → fail-closed, не публикуется/не ставится).

## 13. Критерии приёмки (M8.1)
- Публикация skill/subagent/command/workflow: scan-pass → агентский PR в org → версия+провенанс в реестре.
- Заведомо вредный артефакт (тест-инъекция) → **fail-closed**, не публикуется И не импортируется.
- Импорт делает повторный скан и ставит pinned-версию; конфликт → two-tap overwrite.
- Все вердикты/решения — в неизменяемом аудите; org-PAT нигде в файлах.
- Прогон на 2 тенантах: vitaliy публикует → dmrudenko импортирует (или наоборот).
