# M5.4b — ApprovalsQueue: аппрувы инструментов из Telegram и Mini App

Статус: **ДИЗАЙН — на ревью у Vitaliy** (2026-06-10). Кода нет, пока не согласовано.
Пилот: **vitaliy only** (как весь M1+).

## Задача

Закрыть пробел паритета из [10](10-authoring-miniapp-ide.md): когда Claude Code в
тенант-поде хочет выполнить гейтуемый инструмент, пользователь подтверждает или
отклоняет это **inline-кнопками в Telegram** и/или из экрана **ApprovalsQueue в
Mini App** — не заходя в терминал. Тот же механизм дальше переиспользует M5.5
(гейт на подключение MCP — «гейт на недоверенном входе», см. memory
`feedback_gate_at_untrusted_entry`).

## Поток (happy path)

```
Claude Code (тенант-под)                cp-api (хост)                 Пользователь
────────────────────────                ─────────────                 ────────────
PreToolUse hook (matcher)
  │ POST /approvals  ──────────────────► создаёт approval (PG, pending,
  │   unix socket, peercred-auth          ttl=120s) + audit + Redis pub
  │                                       ├─► Telegram: sendMessage с
  │                                       │   inline-кнопками ✅/❌ (бот аппрувов)
  │                                       └─► ws /live + ws /approvals (Mini App)
  │ GET /approvals/<id>/wait (long-poll)
  │   ◄──────────────────────────────── ответ пользователя:
  │                                       • callback_query → webhook cp-api, или
  │                                       • POST /approvals/<id>/answer из Mini App
  ▼
stdout: {"permissionDecision":"allow"|"deny", "permissionDecisionReason":...}
```

## Решения и почему

1. **Транспорт под→cp-api: unix-сокет, не TCP.** Под имеет proxy-only egress
   (ADR-002) и не должен получать сетевой путь к cp-api. Переиспользуем паттерн
   audit-collector: cp-api открывает второй listener на
   `/run/audit/approvals.sock` в уже расшаренном named volume `cp-audit-run`
   (его монтируют и тенант-под, и cp-api — wiring уже есть в `claude-pod-run`).
   Аутентификация — `SO_PEERCRED`: uid соединившегося процесса = uid тенанта,
   cp-api маппит uid→os_username→user_id. Никаких токенов в поде.

2. **Ответ из Telegram: ОТДЕЛЬНЫЙ бот аппрувов, не основной.** Основной токен
   уже потребляется плагином (getUpdates polling); второй потребитель того же
   токена выселяет первого (инцидент 2026-06-01, memory
   `feedback_workflow_settings_write_kills_telegram_plugin`). Поэтому:
   - новый бот у BotFather (например `@fleet_approvals_bot`), токен — podman
     secret `cp_approvals_bot_token` (как `cp_bot_token`);
   - cp-api ставит ему **webhook** `https://miniapp.ai-assistant.gg/api/tg/approvals`
     (HTTPS уже есть; nginx уже проксирует /api → cp-api);
   - webhook валидируется секретным `X-Telegram-Bot-Api-Secret-Token`.
   Кнопки: «✅ Разрешить» / «❌ Отклонить» (+ «❌ всегда» позже). callback_query
   обновляет approval и редактирует сообщение («✅ разрешено в 14:02»).

3. **Fail-closed.** Таймаут (120s, конфигурируемо) или недоступность cp-api →
   хук возвращает `permissionDecision:"ask"` — НЕ deny: решение падает обратно
   в нативный механизм Claude Code (плагин-флоу в сессии), как сейчас. Так
   новый слой не может ни молча разрешить, ни заблокировать работу бота при
   отказе своей инфраструктуры. Деградация = сегодняшнее поведение.

4. **Какие инструменты гейтуются.** Matcher хука — конфиг тенанта
   (`settings.json` hooks, голден-копия под защитой M4.3). Пилотный набор:
   только то, что сегодня и так требует подтверждения (permission ask). Хук не
   добавляет новых блокировок — он меняет КАНАЛ ответа, не политику.

5. **Аудит.** Каждый `approval.requested` / `approval.answered` (кто, что,
   какой инструмент, payload-превью, решение, канал ответа) → audit-collector
   → WORM + Redis → виден в LiveActivity.

6. **Mini App: экран ApprovalsQueue.** Список pending (+история), кнопки
   Allow/Deny → `POST /approvals/<id>/answer` (JWT). Realtime — через уже
   работающий ws (события `approval.*` приходят в `live:<userId>`; отдельный
   ws-канал не нужен).

## Хранение

`approvals` (PG): `id uuid, user_id, tool, payload jsonb (обрезанный),
status pending|allowed|denied|expired, answered_via tg|miniapp|timeout,
created_at, answered_at, ttl_seconds`. Pending-ожидание хука — long-poll с
Redis pubsub-wakeup (`approval:<id>`), не busy-loop по PG.

## Что НЕ делаем сейчас

- Никакого LLM в цепочке аппрува (правило zero recurring LLM calls не задето —
  тут вообще нет LLM).
- Не трогаем плагин (инвариант «no plugin patch») — его permission-флоу
  остаётся как fallback.
- «Always allow»-правила, батч-аппрувы, аппрувы других ботов — позже.

## Откат (одна команда)

Хук — одна строка в hooks-конфиге тенанта; откат = убрать её из голдена и
`agentshield-rebaseline` (или `git revert` коммита + re-run m1.5 для cp-api).
Без хука вся остальная инфраструктура (эндпоинты, бот) пассивна и безвредна.

## Порядок реализации

1. cp-api: таблица + `/approvals` CRUD + unix-listener + long-poll wait.
2. Approvals-бот: secret, webhook-роут, sendMessage с inline-кнопками,
   callback_query → answer.
3. Хук `approval-gate` (shell, в образе пода / runtime-репо) + matcher в
   голден-настройках vitaliy.
4. Mini App: экран ApprovalsQueue.
5. Приёмка: запросить у бота действие, требующее подтверждения → кнопка в
   Telegram → инструмент выполняется; то же из Mini App; таймаут → fallback
   в нативный ask; всё видно в LiveActivity и WORM-аудите.

Нужно от Vitaliy: **создать бота аппрувов в BotFather** (имя на его вкус) и
прислать токен (уйдёт в podman secret, не в файл), плюс добро на дизайн.
