# M5.4b — ApprovalsQueue: платформенные аппрувы без второго бота

Статус: **ДИЗАЙН v2 — на ревью у Vitaliy** (2026-06-11). Кода нет, пока не согласовано.
Пилот: **vitaliy only** (как весь M1+).

v1 (2026-06-10) предлагал отдельного approvals-бота. **Отклонено Vitaliy**:
inline-кнопки подтверждения инструментов в чате уже есть — это собственный
permission-флоу telegram-плагина (он поллит основной токен и сам обрабатывает
нажатия). Этот флоу остаётся как есть; дублировать его не нужно.

## Что тогда остаётся делать (реальный пробел)

Плагин закрывает аппрувы **внутри сессии Claude Code** (PreToolUse/permission).
Не закрыто другое — **платформенные** аппрувы, где спрашивает не сессия, а
cp-api/control-plane, и сессия вообще может быть ни при чём:

- M5.5: гейт на подключение MCP из Mini App (скан → вердикт → «подключить?»);
- импорт артефактов из маркетплейса ([12](12-artifacts-sharing.md));
- будущие операции из Mini App, требующие подтверждения (удаление, публикация).

Плюс UX-пробел: нет **очереди/истории** аппрувов — что запрашивалось, кем
решено, когда (сейчас кнопка в чате «уехала» вверх — и всё).

## Дизайн v2 — ноль новых ботов, ноль новых слушателей

Ключевой факт Telegram API: конфликт двух потребителей возникает только на
**приёме** обновлений (getUpdates/webhook). `sendMessage` основным токеном —
безопасен. А inline-кнопка типа **url** не генерирует callback_query вообще —
она просто открывает ссылку. Значит:

```
источник запроса (cp-api: гейт MCP, импорт, …)
  → создаёт approval (PG: pending, ttl) + audit + Redis pub
  ├─► уведомление: sendMessage ОСНОВНЫМ токеном (только отправка),
  │     inline url-кнопка «Открыть аппрувы» → t.me/<bot>?startapp=approvals
  └─► Mini App: экран ApprovalsQueue (deep link сразу на него)
        пользователь жмёт ✅/❌ → POST /approvals/<id>/answer (JWT, HTTPS)
  → ожидающий процесс получает ответ (long-poll + Redis wakeup)
```

- **Ответ идёт через Mini App по HTTPS** — Telegram-события не нужны, плагин
  не затронут, второй бот не нужен.
- **Уведомление приходит от основного бота** — привычный чат, кнопка-ссылка
  открывает Mini App прямо на экране очереди (`startapp`-параметр).
- Решение, кто решил (tg user id из initData), канал, время — в **WORM-аудит**
  и в LiveActivity (канал `live:<userId>` уже работает).

## Что НЕ делаем

- НЕ трогаем permission-флоу плагина — кнопки в чате для инструментов сессии
  остаются единственным механизмом там, где они уже работают.
- НЕ заводим второго бота, webhook, второй getUpdates.
- НЕ хук PreToolUse → cp-api (v1, п.1): для сессионных аппрувов он дублировал
  бы плагин. Unix-socket-транспорт из пода отложен до реальной потребности
  (если когда-то захотим аппрувы headless-фоновых задач — отдельный дизайн).
- Никаких LLM в цепочке (правило zero recurring LLM calls не задето).

## Хранение и API (cp-api)

- PG `approvals`: `id, user_id, kind ('mcp.connect'|'artifact.import'|…),
  title, payload jsonb, status pending|allowed|denied|expired,
  answered_via miniapp|timeout, created_at, answered_at, ttl_seconds`.
- `POST /approvals` (внутренний, вызывают другие роуты cp-api — не публичный);
  `GET /approvals?status=` (JWT, своя очередь+история);
  `POST /approvals/:id/answer {allow|deny}` (JWT, только свои, идемпотентно);
  ожидание ответа внутри cp-api — Redis pubsub `approval:<id>`, fail-closed:
  ttl истёк → `expired` = deny.
- Уведомление: sendMessage основным токеном (он уже есть как podman secret
  `cp_bot_token`) + url-кнопка `t.me/<имя бота>?startapp=approvals`.

## Mini App

- Экран **ApprovalsQueue**: pending сверху (✅/❌), ниже история; realtime —
  события `approval.*` уже приходят в ws `/live`.
- Обработка `startapp=approvals` → открыть экран очереди сразу.

## Откат

Аппрувы создаёт только сам cp-api (внутренние вызовы из будущих гейтов M5.5+).
До M5.5 фича пассивна: пустая очередь, ничего не блокирует. Откат = git revert
коммита + re-run m1.5-services.sh (пересоздать cp-api).

## Порядок реализации

1. cp-api: таблица + роуты + ожидание с ttl + уведомление url-кнопкой.
2. Mini App: ApprovalsQueue + deep link `startapp`.
3. Приёмка на тестовом approval'е (ручной POST): уведомление в чат → кнопка →
   Mini App → ✅ → ожидающий запрос разблокирован; ttl → expired=deny;
   всё видно в LiveActivity + WORM.
4. Следом M5.5 (гейт MCP) садится на этот механизм первым реальным клиентом.
